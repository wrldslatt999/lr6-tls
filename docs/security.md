# Безпековий аналіз і рекомендації

## Загрози та захист

| Загроза | Захисний механізм | Перевірка |
|---|---|---|
| Прослуховування каналу | TLS 1.2+ (зазвичай TLS 1.3), серверний cert із SAN | Реальний TLS client-server тест |
| Підміна сервера | Довірений `ca.crt`, `check_hostname=True`, `CERT_REQUIRED` | Неправильний CA та hostname відхиляються |
| Компрометація пароля з БД | `scrypt` з випадковим 128-бітним salt, N=16384/r=8/p=1 | unit tests з верифікацією |
| Перебір паролів | 5 невдалих спроб / 60 сек з однієї IP | інтеграційний тест `rate_limited` |
| Підміна payload | TLS + HMAC-SHA256 за випадковим сесійним ключем | `bad_hmac` |
| Replay | Послідовні номери запитів `seq`, TTL 900 сек, logout | `invalid_sequence` |
| Некоректні повідомлення | Ліміт 64 КіБ на фрейм, 32 КіБ на payload, JSON-валидація | unit/integration tests |
| Несанкціонований обхід входу | Перший запит мусить бути `auth`; токен обов'язковий | `authentication_required` |
| Витік секретів через GitHub/logs | `.gitignore`, заборона CLI-пароля, журнал без raw даних | тести та скрипт публікації |

## Важливі обмеження

1. У сховищі паролів використано **scrypt**, а не bcrypt; це відповідає умові «bcrypt або аналогічне хешування». Параметри N/r/p доцільно калібрувати на цільовому пристрої; поточні — навчальний компроміс.
2. Rate limit і сесії зберігаються у пам'яті **одного** процесу. Для продакшену потрібне централізоване сховище, WAF, per-account обмеження й моніторинг.
3. Локальний CA та приватний ключ підходять **лише для лабораторної**. Рекомендована ізоляція CA-ключа, його ротація та централізоване керування сертифікатами.
4. HMAC-сесійний ключ узгоджений всередині TLS, не є незалежним PSK. Компрометація кінцевої точки руйнує захист.
5. Процес підтримує concurrent connections через потоки; не має промислового захисту від TCP-flood або вичерпання ресурсів. Застосунок за замовчуванням доступний лише через loopback.
6. Формат JSONL — простий локальний audit trail без захисту від видалення адміністратором; для виробництва потрібне пересилання в SIEM і контроль незмінності логів.
7. Сервер не зберігає передані повідомлення, лише метадані/хеш і їх розмір. Це зменшує ризик витоку конфіденційних даних.

## Напрями вдосконалення

- Централізована система відстеження сертифікатів і їх ротація.
- Налаштування коротших TTL, mTLS чи MFA для чутливих систем.
- Сховище секретів замість локального файлу; централізоване rate limiting.
- Уніфікований reverse proxy з fail2ban і журналом усіх TLS-handshake невдач.
- Моніторинг криптографічної конфігурації OpenSSL і залежностей, регулярний аудит.

**Не запускати як публічний інтернет-сервіс** без незалежного аналізу та додаткового hardening.
